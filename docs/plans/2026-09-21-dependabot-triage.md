# Dependabot sweep — measured triage (2026-09-21)

29 open dependabot PRs (`#6599`–`#6627`), all opened 2026-09-21 between 11:05Z and 11:28Z.
This document is the evidence file for the goal prompt
[`docs/goal-prompt-dependabot-2026-09-21.txt`](../goal-prompt-dependabot-2026-09-21.txt).
Every verdict below was measured in this sandbox against `main` @ `eeb30e18`, not inferred from
PR titles. Reproduction commands are inline so each claim can be re-checked.

## Headline

**Zero of the 29 PRs is mergeable as-is**, and not for the usual reason. The pip group is not
"waiting on CI" — it is *structurally invalid*: dependabot is misconfigured for this repo's
Python lockfile, so it edits a generated file and proposes versions its own resolver rejects.
The npm and Docker groups are genuine upgrades blocked by couplings dependabot cannot see
(companion bumps, an SSOT gate, an upstream support ceiling).

Three configuration defects in `.github/dependabot.yml` are the root cause of most of it. Fixing
those is cheaper than processing the PRs, and processing the PRs without fixing them just
regenerates the same 29 next Monday.

## Why every ecosystem is exactly at its PR limit

| Ecosystem | Open PRs | `open-pull-requests-limit` |
| --- | --- | --- |
| `pip` (`/`) | 10 | 10 |
| `npm` (`/frontend`) | 10 | 10 |
| `github-actions` (`/`) | 5 | 5 |
| `docker` (4 dirs) | 1 of 3 each | 3 |

All four are saturated. Dependabot will not open the *correct* PRs (e.g. vite 7 → 8, needed by
`@vitejs/plugin-react` 6) until the queue drains. Closing/stale-ing is therefore load-bearing
work, not tidiness.

## Also: CI noise to ignore

`Trivy` reports `conclusion: neutral` on **all 29** PRs. It is a code-scanning annotation
(check-run, not a job); on `main` push runs every real Trivy job is `success`. **It is not a
blocker on any PR** — do not chase it.

Genuinely ambient red, present on non-dependabot PRs too: `Smoke Test Deployment`,
`SBOM & Sign (frontend)`, `Rollback to Stable Images`, `Create Linear Issue on Main CI Failure`,
`Nightly status`, `Backend full gate (validate.sh semantics)`. Judge a PR only on the checks
that gate: `CI Gate (Required Checks)`, `Version Consistency`, `Collection Sanity`,
`Frontend Type Check`, `Frontend Lint`, `Frontend Tests`, `Test Coverage Gate`.

## Group A — Python: all 10 PRs are invalid as authored

`#6618`–`#6627`. **All ten touch only `requirements-audit.txt`.** None touches
`pyproject.toml` or `uv.lock`.

That file is generated. Its own header says so:

```
# This file was autogenerated by uv via the following command:
#    uv export --no-hashes
```

Every consumer regenerates it before use — `dependency-audit.yml:51`,
`vulnerability-management.yml:46`, `weekly-audit.yml:41` all run
`uv export --no-hashes > requirements-audit.txt`. `scripts/audit-summary.sh` writes it to `/tmp`
and deletes it. **Nothing in the repo reads the committed copy.** It is decorative, and there is
no drift check that would notice it going stale.

So a merged pip PR changes a file nothing reads, and the environment actually installed by
`uv sync --frozen` does not move. The PR is a no-op wearing a version bump.

### Root cause: wrong ecosystem

`.github/dependabot.yml` declares `package-ecosystem: 'pip'` for `/`. This repo's Python lockfile
is **`uv.lock`**, governed by `pyproject.toml`. The `pip` ecosystem reads requirements-format
files and does not understand uv's universal lock, extra/groups graph, or `tool.uv` constraints —
which is why it targeted the exported artifact instead of the lock. Dependabot has a dedicated
`uv` ecosystem for exactly this; the config predates the uv migration (the `pip` entry arrived in
`c57db1fc`, PR #394).

call than the user's stated "wont-upgrade because unstable" — see Rulings.

### Two real defects found while measuring

1. **`data-designer-engine==0.9.2` ships self-contradictory metadata.** Its `requires_dist`
   declares `fsspec<2026,>=2025.3.0` and `faker<21,>=20.1.0`, while some extra of the same
   version pins `fsspec==2026.7.0` and `faker==40.39.0`. Both cannot hold. uv's error surfaces
   this contradiction directly. Worth an upstream issue — it makes the package unresolvable on
   whichever axis you pick.

2. **`scripts/audit-summary.sh:70,73` calls `uv run radon cc|mi`, but `radon` is not a direct
   dependency** — it is a transitive of `wily`, with a comment in `pyproject.toml:138`
   acknowledging it (`# Note: radon is provided by wily dependency (5.1.x)`). Any fix that
   removes `wily` must add `radon` explicitly or that script breaks silently (`|| true` hides it).

### Is `wily` even load-bearing?

`nightly.yml:35,39,40` runs it as `uv tool run wily …` — **isolated from the project
environment**, so it does not need the project's `wily` pin at all. The project-env `wily` in
`dev`/`quality` exists only to satisfy that radon call. Dropping `wily` from both groups and
adding `radon` directly would unblock plotly/radon/colorlog/mando in one edit. **Ruling R-1.**

### #6607 TypeScript 7 — the hard ceiling

Measured, in order:

1. `tsc --noEmit` fails with 2 errors, both removed-option errors in `tsconfig.json`:
   `TS5102 baseUrl has been removed`, `TS5090 Non-relative paths are not allowed`.
2. The fix is small and confirmed: drop `"baseUrl": "."`, rewrite `"@/*": ["src/*"]` →
   `["./src/*"]`. Vite is unaffected — its alias is its own
   (`vite.config.ts:170` `path.resolve(__dirname,'./src')`).
3. With that applied, TS7 reports **exactly 1 code error**:
   `src/hooks/webSocketManager.ts:317` TS2345 `Uint8Array<ArrayBufferLike>` not assignable to
   `string | Blob | BufferSource` (stricter `ArrayBufferLike` typing).
4. **The blocker is not the code.** `npx eslint` throws:
   ```
   Error: typescript-eslint does not support TS 7.0.
   ```
   `typescript-eslint` 8.70.0 — the current latest — declares
   `typescript: ">=4.8.4 <6.1.0"`. **Zero released versions accept TS 7.** The frontend lint
   gate cannot run at all on TS7.
5. `typedoc` caps at `typescript: 5.0.x … 6.0.x` — also excludes 7.

**TypeScript 6.0.3 is the correct intermediate and is genuinely landable.** Measured: eslint
passes (rc=0), and tsc reports exactly one advisory —
`TS5101 Option 'baseUrl' is deprecated and will stop functioning in TypeScript 7.0` — silenced
by `"ignoreDeprecations": "6.0"`, or properly by applying the tsconfig migration above now,
which is needed either way. Dependabot proposed 5.9.3→7.0.2 straight past 6 because 6 sat
between the old pin and the new latest; nobody proposed the intermediate.

### #6604 vitest 5 — small, concrete fix

`tsc --noEmit` reports exactly one error:

```
src/__tests__/matchers.ts(127,13): error TS2428: All declarations of 'Assertion' must have identical type parameters.
```

`src/__tests__/matchers.ts:127` declares `interface Assertion<T = any>` inside
`declare module 'vitest'`; Vitest 5 changed the interface's own parameter list, so the
augmentation no longer matches. Fix is a one-line signature alignment. Note the installed tree
shows `vitest 5.0.1` alongside `typescript 5.9.3` — these are independent; this PR does not
require #6607.

### #6602 Node 26 — fails the repo's own SSOT gate, and isn't LTS

Exactly 1 gate failure, reproduced locally in one command:

```
$ bash scripts/check-version-consistency.sh /tmp/wt-node
FAIL: frontend/Dockerfile:22 base node:26 != .nvmrc major (24)
```

`scripts/check-version-consistency.sh` is deliberate — its header records why ("the 3.11 fiction"
class: ci.yml labels said 3.11 while uv ran 3.14, and triage paid for it). A Node major is a
whole-repo change that must flip, in one commit:

- `.nvmrc` (`24`) — the source of truth
- `frontend/Dockerfile:22` `FROM node:24.21.0-alpine3.23`
- `frontend/package.json` `engines: "^22.12.0 || >=24.0.0"` — must admit `>=26.0.0`
- **21 workflow literals**: 16 × `NODE_VERSION: '24'` + 5 × `node-version: '24'`
- `scripts/validate.sh:31` fallback default `24`

Independently: **Node 26 is not LTS yet.** From the nodejs/Release schedule, `v26` starts
2026-05-05 and reaches LTS on **2026-10-28** — five weeks out. Current Node 24 is already in
Maintenance (since 2026-10-20 — i.e. now). Waiting ~5 weeks for Node 26 LTS and taking it as a
planned change beats carrying a 25-file churn PR. **Defer.**

## The three config defects that generated this pile

Processing 29 PRs without touching `.github/dependabot.yml` reproduces the same 29 next Monday
at 11:00Z. These are the fixes, in value order:

1. **`pip` → `uv` ecosystem.** The `pip` entry at `/` reads requirements-format files and cannot
   model `uv.lock`, so it targets the exported artifact and ignores
   `pyproject.toml`'s actual constraint graph. The dedicated `uv` ecosystem exists for this
   and it would resolve through the real graph — which means it would stop proposing
   the eight versions uv itself refuses. Config predates the uv migration (added `c57db1fc`,
   PR #394). *String CONFIRMED 2026-09-21 (measured, no longer a guess):
   `package-ecosystem: 'uv'` — github/docs raw source
   `content/code-security/reference/supply-chain-security/dependabot-options-reference.md`
   ecosystem table: "| uv | `uv` | v0.11 |" (pip/pip-compile/pipenv/poetry all map to `pip`);
   dependabot-core ships a dedicated `uv/` package whose file_fetcher requires `uv.lock` +
   `pyproject.toml` (file_fetcher.rb:19,24,37), so `directory: '/'` stays as-is.*

   **KNOWN SCOPE — the switch is not a pure cleanup (measured).** PR #6544 (merge commit
   `d1546bee`, 2026-09-15, authored by dependabot[bot], grouped under "the uv group") edited
   THREE files: `uv.lock` +125/−63-ish, `requirements-audit.txt` 30 lines, AND hand-written
   `ai/florence/requirements.txt` 10 lines — lifting floors `torch>=2.0.0`→`>=2.14.0`,
   `transformers>=4.49.0,<5.0.0`→`>=5.17.0,<6.0.0`, `pillow>=10.0.0`→`>=12.3.0`,
   `accelerate>=0.25.0`→`>=1.15.0`, `python-multipart>=0.0.6`→`>=0.0.32`. That file is a real
   container build input (`ai/florence/Dockerfile:48,50` COPY + `uv pip install -r`). The
   config at that PR's base (`15d7b5a244`) is byte-identical to today's — one config, one
   dependabot[bot] root commit, no second config ever existed — so the `uv`-labelled group IS
   what rewrote those floors. Consequence: after the switch, dependabot will keep touching
   `ai/*/requirements.txt` floors, and NO CI job validates those floors
   (`build-base-image.yml:9,16` triggers only on `requirements-base.txt`) — those hunks need
   human review, and the config should carry a comment saying so.

2. **Untrack `requirements-audit.txt`, gitignore it, and drop it from dependabot's view.**
   Nothing reads the committed copy; all three audit workflows regenerate it and
   `audit-summary.sh` uses `/tmp`. Keeping it tracked guarantees dependabot keeps filing PRs
   against a decorative file. If a committed snapshot is genuinely wanted for diff-visibility,
   generate it in CI as an artifact instead.

3. **Groups are `minor|patch` only, so every major-coupling is invisible.** This is why #6608
   (plugin-react 6) arrived without its required vite 8 peer, and why the Stryker family
   arrives one member at a time. Options: add explicit `major` groups for the coupled families
   (react ecosystem, vite/tooling, stryker), or accept that majors need a human-authored
   branch. Also add a group covering all four `@stryker-mutator/*` packages so they move
   together.

Two smaller gaps: `/ai/gateway`, `/ai/triton` and the root `Dockerfile.yolo26-benchmark` have
no docker ecosystem entry, so three stale base images are permanently invisible to dependabot;
and `ignore` conditions would let dependabot stop filing the known-blocked majors (e.g.
`typescript` ≥7 until typescript-eslint supports it) instead of re-opening them weekly.
